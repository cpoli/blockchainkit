Breakthroughs in Cryptography
=============================

.. include:: /_generated/nav/crypto.rst

.. epigraph::

   "We stand today on the brink of a revolution in cryptography."
   -- Whitfield Diffie and Martin Hellman, *New Directions in Cryptography*,
   1976

Every later idea in a blockchain rests on cryptography: a way to agree on a
secret in public, to prove who authorized a message, and to commit to data
without revealing it. This chronology traces the ideas behind
:mod:`blockchainkit.crypto`, from the one-time pad to Schnorr
multi-signatures. Each entry states the problem, the mechanism that solves it,
and the reason the mechanism works, so the argument can be followed step by
step. Parameters are deliberately small so every value can be inspected;
:doc:`/protocol` lists exactly where the package departs from deployed
systems.

1917-1949 -- The One-Time Pad and Perfect Secrecy
-------------------------------------------------

Gilbert Vernam built a teleprinter in 1917 that combined each character of a
message with a character of a key tape, and Joseph Mauborgne added the rule
that the tape must be random and never reused. Claude Shannon's 1949 theory
of secrecy systems proved why this is unbreakable. Fix a ciphertext
:math:`c`. For every candidate message :math:`m` of the same length there is
exactly one key, :math:`k = c \oplus m`, that produces it, and a uniformly
random key makes all of those keys equally likely. The ciphertext therefore
gives no reason to prefer one message over another:

.. math::

   c = m \oplus k, \qquad m = c \oplus k, \qquad
   \Pr[M = m \mid C = c] = \Pr[M = m].

The argument needs both rules. Reusing the key gives
:math:`c_1 \oplus c_2 = m_1 \oplus m_2`, in which the key has cancelled out;
Soviet reuse of pads let the US Venona project read thousands of messages.
Shannon also showed that every perfectly secret cipher needs at least as much
key as message, which makes the pad impractical for exactly the reason it
works: the two parties must already share a secret as long as everything they
will ever say. That key-distribution problem is what public-key cryptography
would solve.

*Implementation:* :func:`blockchainkit.crypto.systems.one_time_pad.one_time_pad`
refuses a key of the wrong length;
:func:`blockchainkit.crypto.systems.one_time_pad.xor_bytes` is the underlying
operation.

*References:* G. S. Vernam, *Cipher Printing Telegraph Systems for Secret Wire
and Radio Telegraphic Communications*, Journal of the American Institute of
Electrical Engineers 45, 109–115 (1926). C. E. Shannon, *Communication Theory
of Secrecy Systems*, Bell System Technical Journal 28(4), 656–715 (1949). `DOI
<https://doi.org/10.1002/j.1538-7305.1949.tb00928.x>`__.

1971 -- Baby-Step Giant-Step: Square-Root Discrete Logs
-------------------------------------------------------

In a cyclic group of order :math:`n` generated by :math:`g`, computing
:math:`h = g^x` from :math:`x` is fast, but the reverse, the *discrete
logarithm* :math:`x` of :math:`h`, has no obvious shortcut: trying every
exponent takes up to :math:`n` steps. Most of the public-key systems below
are secure only because this reverse direction is hard, so the first question
is how hard it really is. Daniel Shanks, studying class numbers of quadratic
fields, traded memory for time to need only about :math:`\sqrt n` steps.
Every exponent below :math:`n` can be written as :math:`x = im + j` with
:math:`m = \lceil\sqrt n\,\rceil` and :math:`0 \le i, j < m`. Multiplying
:math:`g^{im + j} = h` by :math:`g^{-im}` separates the two unknowns:

.. math::

   g^{x} = h \iff g^{j} = h\,(g^{-m})^{i}, \qquad
   \text{cost} \approx 2\sqrt{n}.

So store the :math:`m` "baby steps" :math:`g^j` in a table, then take "giant
steps" :math:`h, hg^{-m}, hg^{-2m}, \dots` until one appears in the table;
the matching :math:`i` and :math:`j` give :math:`x`. Generic algorithms cannot
do fundamentally better: Shoup proved in 1997 that any algorithm using only
the group operations needs about :math:`\sqrt n` steps. For well-chosen
elliptic curves no attack better than these generic ones is known, which is
why a group of about :math:`2^{256}` elements gives about 128-bit security.

*Implementation:* :func:`blockchainkit.crypto.systems.discrete_log.baby_step_giant_step`
returns the exponent and the number of table multiplications.

*References:* D. Shanks, *Class Number, a Theory of Factorization, and
Genera*, Proceedings of Symposia in Pure Mathematics 20, American Mathematical
Society, 415–440 (1971).

1974-1978 -- Merkle's Puzzles: Key Agreement in Public
------------------------------------------------------

As an undergraduate in 1974, Ralph Merkle proposed the first scheme for two
parties to agree on a secret over a public channel, attacking the
key-distribution problem left by the one-time pad. Alice publishes
:math:`N` puzzles. Each one seals a random identifier and a random session key
under a deliberately weak key, so it can be opened by brute force in about
:math:`N` trials. Alice keeps a private table from identifiers to session keys.
Bob opens one puzzle chosen at random and announces only its identifier; Alice
looks the identifier up, and both now hold the same session key. An
eavesdropper hears the identifier but does not know which puzzle contains it,
so they must open puzzles until they find it, about :math:`N/2` of them on
average:

.. math::

   W_{\text{honest}} = O(N), \qquad
   W_{\text{attacker}} \approx \tfrac{N}{2} \cdot N = O(N^2).

The idea was hard to publish, and the paper appeared in 1978, after Diffie and
Hellman's. A quadratic gap is not practical security: an attacker with a
thousand times Bob's computing power can still keep up with a thousand-fold
larger :math:`N`. Diffie-Hellman replaced it with a gap that grows
exponentially in the key size. But the puzzles showed that public key
agreement was possible at all, and Barak and Mahmoody later proved (2009) that
the quadratic gap is the best any scheme built only from a random function can
achieve.

*Implementation:* :func:`blockchainkit.crypto.systems.puzzles.merkle_puzzles`
creates the puzzles and Alice's table;
:func:`blockchainkit.crypto.systems.puzzles.solve_puzzle` opens one by brute
force.

*References:* R. C. Merkle, *Secure Communications over Insecure Channels*,
Communications of the ACM 21(4), 294–299 (1978). `DOI
<https://doi.org/10.1145/359460.359473>`__.

1976 -- Diffie-Hellman: Agreeing on a Secret over a Public Channel
------------------------------------------------------------------

Sharing an encryption key used to require a secret channel in advance. Diffie
and Hellman asked whether two people could reach the same secret by
exchanging only public values. In their construction each party raises a
public generator :math:`g` to a private exponent, publishes the result, and
raises the other's public value to the same private exponent. Because
exponents multiply in either order, both arrive at the same element:

.. math::

   A=g^a\bmod p,\qquad B=g^b\bmod p,\qquad
   B^a=(g^b)^a=g^{ab}=(g^a)^b=A^b \pmod p.

An observer sees :math:`g, p, A, B`. The only known general way to compute
:math:`g^{ab}` from them is to recover :math:`a` or :math:`b`, which is a
discrete logarithm, and the 1971 entry shows its generic cost is about
:math:`\sqrt n`. The honest parties do one exponentiation each, about
:math:`\log_2 n` multiplications, so the gap between them and the attacker
grows exponentially with the key size. The exchange does not say who is at
the other end: an attacker who substitutes their own public value shares one
secret with each party and can relay between them. Deployed protocols
therefore authenticate the exchange and pass the shared element through a key
derivation function.

*Implementation:* :class:`blockchainkit.crypto.systems.asymmetric.DHGroup`
validates the prime-order subgroup and peer elements. It runs in a 62-bit
teaching group with no authentication; deployments use 2048-bit groups or
X25519.

*References:* W. Diffie and M. E. Hellman, *New Directions in Cryptography*,
IEEE Transactions on Information Theory 22(6), 644–654 (1976). `DOI
<https://doi.org/10.1109/TIT.1976.1055638>`__; `author's copy
<https://ee.stanford.edu/~hellman/publications/24.pdf>`__.

1978 -- RSA and the Public Trapdoor
-----------------------------------

Diffie-Hellman agrees on a key but does not let anyone encrypt to, or verify a
signature from, a published key. Rivest, Shamir and Adleman gave the first
concrete system with a *trapdoor*: a public operation that anyone can apply,
and a private one that reverses it. Choose distinct primes :math:`p, q`,
publish :math:`n = pq` and an exponent :math:`e`, and keep the inverse
exponent :math:`d`:

.. math::

   ed\equiv1\pmod{(p-1)(q-1)},\qquad
   c=m^e\bmod n,\qquad m=c^d\bmod n.

Decryption works because :math:`ed = 1 + k(p-1)(q-1)` for some integer
:math:`k`, and Euler's theorem gives :math:`m^{(p-1)(q-1)} \equiv 1`, so
:math:`c^d = m^{ed} = m \cdot (m^{(p-1)(q-1)})^k \equiv m \pmod n`. Finding
:math:`d` requires :math:`(p-1)(q-1)`, which requires the factors of
:math:`n`; computing :math:`d` from :math:`e` is in fact as hard as factoring.
Security therefore rests on factoring being hard, though no proof shows that
decrypting without :math:`d` is equally hard.

*Implementation:* :func:`blockchainkit.crypto.systems.asymmetric.rsa_keypair`
exposes the arithmetic, with the familiar :math:`61\times53` example. This is
textbook RSA: tiny primes and no padding, so it is deterministic (equal
messages give equal ciphertexts) and malleable (multiplying ciphertexts
multiplies plaintexts). Real RSA uses moduli of 2048 bits or more with OAEP
(encryption) or PSS (signatures) padding.

*References:* R. L. Rivest, A. Shamir, and L. Adleman, *A Method for Obtaining
Digital Signatures and Public-Key Cryptosystems*, Communications of the ACM
21(2), 120–126 (1978). `DOI <https://doi.org/10.1145/359340.359342>`__.

1978 -- Pohlig-Hellman: Why the Group Order Needs a Large Prime Factor
----------------------------------------------------------------------

The :math:`\sqrt n` cost of the 1971 entry assumes the group cannot be taken
apart. Pohlig and Hellman showed that if its order factors as
:math:`n = \prod p_i^{e_i}`, the problem splits into one small problem per
prime power. Raising :math:`g` and :math:`h` to the power
:math:`n/p_i^{e_i}` maps them into the subgroup of order :math:`p_i^{e_i}`,
where the same equation reveals :math:`x` modulo :math:`p_i^{e_i}`:

.. math::

   g_i = g^{n/p_i^{e_i}},\quad h_i = h^{n/p_i^{e_i}}
   \;\Longrightarrow\; h_i = g_i^{\,x \bmod p_i^{e_i}}, \qquad
   \text{cost} \approx \sum_i e_i \sqrt{p_i}.

Each of these is solved one base-:math:`p_i` digit at a time, each digit a
discrete log in a subgroup of order only :math:`p_i`, and the Chinese
Remainder Theorem combines the residues into :math:`x \bmod n`. The cost is
governed by the largest prime factor of :math:`n`, not by :math:`n` itself.
That is why Diffie-Hellman and Schnorr run in a subgroup of large prime order,
and why :data:`blockchainkit.crypto.systems.asymmetric.TEACHING_GROUP` uses a
safe prime :math:`p = 2q + 1` with :math:`q` prime: the subgroup of order
:math:`q` has no smaller pieces to split off.

*Implementation:* :func:`blockchainkit.crypto.systems.discrete_log.pohlig_hellman`
factors the order by trial division, solves each prime-power part with
baby-step giant-step, and combines the answers.

*References:* S. Pohlig and M. Hellman, *An Improved Algorithm for Computing
Logarithms over GF(p) and Its Cryptographic Significance*, IEEE Transactions on
Information Theory 24(1), 106–110 (1978). `DOI
<https://doi.org/10.1109/TIT.1978.1055817>`__.

1979 -- Shamir's Threshold Secret Sharing
-----------------------------------------

A secret stored in one place is a single point of loss or compromise. Shamir
split it among :math:`n` people so that any :math:`t` of them can recover it,
while fewer learn nothing. The secret :math:`s` is the constant term of a
random polynomial of degree at most :math:`t-1` over a prime field, and person
:math:`i` holds the share :math:`f(i)`:

.. math::

   f(x)=s+a_1x+\cdots+a_{t-1}x^{t-1}\pmod p,
   \qquad s=f(0).

A polynomial of degree at most :math:`t-1` is determined by any :math:`t` of
its points, so :math:`t` shares fix :math:`f` and Lagrange interpolation
returns :math:`f(0)`. With only :math:`t-1` shares, every candidate secret
:math:`s'` still fits: the :math:`t-1` points together with :math:`(0, s')`
are :math:`t` points, which define exactly one polynomial. Since the
coefficients are uniform, each candidate is equally likely, so the guarantee
is information-theoretic, not a computational hardness assumption.

*Implementation:* :func:`blockchainkit.crypto.systems.sharing.split_secret` and
:func:`blockchainkit.crypto.systems.sharing.recover_secret` use integer field
arithmetic.

*References:* A. Shamir, *How to Share a Secret*, Communications of the ACM
22(11), 612–613 (1979). `DOI <https://doi.org/10.1145/359168.359176>`__.

1979 -- Lamport's One-Time Signatures from a Hash
-------------------------------------------------

RSA signatures rest on number theory. Leslie Lamport showed that a one-way
function alone suffices. The private key is 256 pairs of random strings
:math:`x_{i,b}` and the public key their hashes. For each bit :math:`b_i` of
:math:`H(m)`, the signer reveals :math:`x_{i,b_i}`, and the verifier checks
:math:`H(x_{i,b_i}) = y_{i,b_i}`:

.. math::

   \text{public key } y_{i,b} = H(x_{i,b}), \qquad
   \sigma = (x_{1,b_1}, \dots, x_{256,b_{256}}).

A forger needs, for every position, the preimage selected by the new
message's hash bit, and producing an unrevealed one means inverting
:math:`H`. Each signature, however, reveals half of the private key. After
:math:`k` signatures on random messages, a given preimage has been revealed
with probability :math:`1 - 2^{-k}`, so a fresh random message can be forged
with probability about :math:`(1 - 2^{-k})^{256}`, which reaches 78% at
:math:`k = 10`. An attacker who can try many messages does far better, so a
key must sign only once. Merkle's trees, invented the same year, authenticate
many one-time keys under one root. Because they rely only on hashing, these
signatures resist quantum computers: the standardized SPHINCS+ (SLH-DSA)
descends from them.

*Implementation:* :func:`blockchainkit.crypto.systems.lamport.lamport_keypair`,
:func:`blockchainkit.crypto.systems.lamport.lamport_sign`, and
:func:`blockchainkit.crypto.systems.lamport.lamport_verify` use full Lamport
pairs. Deployed hash-based signatures (XMSS, SPHINCS+) shrink them with
Winternitz chains and many-time trees.

*References:* L. Lamport, *Constructing Digital Signatures from a One Way
Function*, Technical Report CSL-98, SRI International (1979).

1979 -- Yuval's Birthday Attack
-------------------------------

Finding two people with the same birthday in a room is much easier than
finding someone with *your* birthday, because every pair of people is a
chance for a match. Gideon Yuval turned this into an attack on signatures,
which sign the hash of a message rather than the message itself: prepare many
harmless and many harmful variants of a contract until one of each shares a
hash, have the victim sign the harmless one, and the signature also fits the
harmful one. Among :math:`q` random :math:`n`-bit values there are about
:math:`q^2/2` pairs, each equal with probability :math:`2^{-n}`, so a repeat
appears with probability about :math:`q^2/2^{n+1}` while that is small:

.. math::

   \Pr[\text{collision}] \approx 1 - e^{-q^2 / 2^{n+1}}, \qquad
   E[q] \approx \sqrt{\tfrac{\pi}{2}\, 2^{n}}.

A collision is expected after about :math:`2^{n/2}` hashes, so an
:math:`n`-bit hash gives only :math:`n/2` bits of collision resistance. That
is why SHA-256's 256-bit output is chosen for 128-bit collision security.

*Implementation:* :func:`blockchainkit.crypto.systems.hashing.find_collision`
searches truncated SHA-256;
:func:`blockchainkit.crypto.systems.hashing.truncated_hash` does the
truncation.

*References:* G. Yuval, *How to Swindle Rabin*, Cryptologia 3(3), 187–191
(1979). `DOI <https://doi.org/10.1080/0161-117991854025>`__.

1981 -- Blum's Coin Flipping by Telephone: Commitments
------------------------------------------------------

Manuel Blum asked how two people who do not trust each other can flip a fair
coin over the telephone. Alice seals her call, heads or tails, in an envelope
and sends it; Bob then announces a coin flip; Alice opens the envelope, and
she wins if the call matches. Each property of the envelope stops one cheat.
It must be *binding*, so Alice cannot open it to the other call after hearing
the flip, and *hiding*, so Bob cannot read the call and announce the opposite.
Such an envelope is a *commitment*. With a hash and a random salt :math:`r`:

.. math::

   C = H(\text{domain} \,\|\, |r| \,\|\, r \,\|\, m), \qquad
   \text{open}: (m, r) \ \text{with}\ H(\dots) = C.

Opening to a different value means finding a second input with the same hash,
so binding rests on collision resistance. Without the salt, hiding would fail:
Bob could simply hash "heads" and "tails" and compare. A long random salt
makes such guessing hopeless. Encoding the salt's length :math:`|r|` fixes
where the salt ends and the message begins, so one input cannot be split two
ways. Commitments became a basic building block: a Schnorr prover commits to
:math:`R` before seeing a challenge, and a block header commits to its
transactions.

*Implementation:* :func:`blockchainkit.crypto.systems.commitments.commit` adds
domain separation and explicit salt framing;
:func:`blockchainkit.crypto.systems.commitments.verify_commitment` compares in
constant time.

*References:* M. Blum, *Coin Flipping by Telephone: A Protocol for Solving
Impossible Problems*, CRYPTO '81, 11–15 (1981); reprinted in ACM SIGACT News
15(1), 23–27 (1983). `DOI <https://doi.org/10.1145/1008908.1008911>`__.

1982-1983 -- Chaum's Blind Signatures and Private Payments
----------------------------------------------------------

To spend digital cash privately, a bank must authorize a token without
learning which token it signed: like stamping an envelope without seeing the
letter inside. David Chaum introduced blind signatures at CRYPTO '82
(proceedings 1983). RSA's algebra lets the requester hide a message with an
invertible random factor :math:`r` and remove it after signing:

.. math::

   m'=mr^e\bmod n,\qquad
   s'=(m')^d\bmod n,\qquad
   s=s'r^{-1}\bmod n.

The factor cancels because :math:`(r^e)^d = r`: :math:`s' = m^d r`, so
:math:`s = m^d` and :math:`s^e = m \pmod n`. The requester holds an ordinary
signature on :math:`m`. The signer saw only :math:`m'`, and since :math:`r` is
uniform and raising to :math:`e` permutes the residues, :math:`m'` is uniform
whatever :math:`m` is, so it reveals nothing about the token.

*Implementation:* :func:`blockchainkit.crypto.systems.asymmetric.rsa_blind` and
:func:`blockchainkit.crypto.systems.asymmetric.rsa_unblind` expose this
identity with textbook RSA over a tiny modulus. Standardized blind RSA (RFC
9474) hashes and pads the message and uses full-size keys.

*References:* D. Chaum, *Blind Signatures for Untraceable Payments*, CRYPTO
'82, 199–203 (proceedings 1983). `DOI
<https://doi.org/10.1007/978-1-4757-0602-4_18>`__.

.. minigallery:: ../../examples/crypto/blind_signatures/plot_01_blind_signatures.py

1985 -- Elliptic Curves as a Cryptographic Group
------------------------------------------------

Diffie-Hellman needs only a group in which discrete logs are hard, not
specifically the integers modulo :math:`p`. Victor Miller proposed elliptic
curves for this at CRYPTO '85, and Neal Koblitz independently developed
elliptic-curve cryptosystems. The group is a finite set of curve points with
a special addition rule, not a smooth curve over the real numbers. A private
key is an integer :math:`x`; the public key is the base point :math:`G` added
to itself :math:`x` times:

.. math::

   y^2=x^3+ax+b\pmod p,\qquad Q=xG.

Double-and-add computes :math:`Q` in about :math:`2\log_2 x` additions;
recovering :math:`x` from :math:`G, Q` is the elliptic-curve discrete-log
problem. The integers modulo :math:`p` have extra structure, such as
factorization into primes, that index-calculus algorithms exploit to solve
discrete logs (and factor RSA moduli) in subexponential time, so those keys
must be thousands of bits long. No such attack is known for well-chosen
curves, leaving only the :math:`\sqrt n` generic attacks, so a 256-bit curve
key matches a roughly 3072-bit RSA key. "Well-chosen" matters: a curve whose
order has only small prime factors falls to Pohlig-Hellman, and some special
families reduce to easier problems.

*Implementation:* :class:`blockchainkit.crypto.systems.curves.Curve`,
:func:`blockchainkit.crypto.systems.curves.add`, and
:func:`blockchainkit.crypto.systems.curves.multiply` implement the group law,
including infinity, inverse points, and doubling. ``TOY_CURVE`` has 19 points;
``SECP256K1`` is Bitcoin's curve. The arithmetic is variable-time Python;
production libraries such as libsecp256k1 use constant-time code, because
timing can leak private scalars.

*References:* V. S. Miller, *Use of Elliptic Curves in Cryptography*, CRYPTO
'85, LNCS 218, 417–426 (proceedings 1986). `DOI
<https://doi.org/10.1007/3-540-39799-X_31>`__. N. Koblitz, *Elliptic Curve
Cryptosystems*, Mathematics of Computation 48(177), 203–209 (1987). `DOI
<https://doi.org/10.1090/S0025-5718-1987-0866109-5>`__.

1985 -- Zero Knowledge: Proofs That Reveal Nothing
--------------------------------------------------

Goldwasser, Micali and Rackoff formalized a striking possibility: an
interaction can convince a verifier that a statement is true while revealing
nothing else. A proof is *zero-knowledge* if a simulator, without the secret,
can produce transcripts indistinguishable from real ones. The verifier could
have generated such transcripts alone, so the real ones cannot have taught
them anything.

Schnorr's later identification protocol shows the idea concretely. A prover
with secret :math:`x` and public key :math:`Q = xG` commits to :math:`R = kG`
for a random :math:`k`, receives a random challenge :math:`c`, and answers
:math:`s = k + cx`; the verifier checks :math:`sG = R + cQ`. A simulator who
picks :math:`c` and :math:`s` first can solve that equation for a matching
:math:`R`:

.. math::

   R = kG,\quad c \xleftarrow{\$} \mathbb{Z}_n,\quad s = k + cx;
   \qquad \text{simulator: } R = sG - cQ.

The proof still convinces a live verifier, because a prover who could answer
two different challenges :math:`c_1 \ne c_2` for the same :math:`R` would know
:math:`x = (s_1 - s_2)/(c_1 - c_2)`. Without :math:`x`, a cheating prover
succeeds only by guessing :math:`c` before committing, with probability
:math:`1/n`. So a real prover must commit to :math:`R` before seeing an
unpredictable :math:`c`. That order is the only thing separating a proof from
a simulation, so a recorded transcript proves nothing to a third party. (The
simulation argument assumes the verifier picks :math:`c` at random, as an
honest one does.)

*Implementation:* :func:`blockchainkit.crypto.systems.signatures.verify_transcript`
checks the group equation;
:func:`blockchainkit.crypto.systems.signatures.simulate_transcript` is the
simulator.

*References:* S. Goldwasser, S. Micali, and C. Rackoff, *The Knowledge
Complexity of Interactive Proof-Systems*, STOC '85, 291–304 (1985). `DOI
<https://doi.org/10.1145/22145.22178>`__.

1986 -- The Fiat-Shamir Heuristic: From Interaction to Signatures
-----------------------------------------------------------------

An interactive proof convinces only the verifier who took part. Fiat and
Shamir replaced the verifier's random challenge with a hash of the transcript
so far. The proof no longer needs a live conversation, and putting the message
into the hash turns it into a signature:

.. math::

   c = H(R, Q, m), \qquad \sigma = (R,\ s = k + cx).

The simulator's trick was to pick :math:`c` first and then solve for
:math:`R`. Now :math:`c` is computed from :math:`R`, and if :math:`H` behaves
like a random function, any change to :math:`R` produces an unpredictable new
:math:`c`, so the trick no longer works and a valid :math:`(R, s)` again shows
knowledge of :math:`x`. Pointcheval and Stern later proved such signatures
secure in this random-oracle model. Everything the verifier would have seen
must go into the hash: leaving out :math:`Q`, for instance, lets an attacker
choose the public key after the challenge. Schnorr signatures, EdDSA, and most
zero-knowledge proof systems used by blockchains (SNARKs, STARKs) rely on this
transform, and such omissions have broken real implementations (the 2022
"Frozen Heart" disclosures).

*Implementation:* :func:`blockchainkit.crypto.systems.signatures.challenge`
hashes the curve domain, public key, commitment, and message.

*References:* A. Fiat and A. Shamir, *How To Prove Yourself: Practical
Solutions to Identification and Signature Problems*, CRYPTO '86, LNCS 263,
186–194 (proceedings 1987). `DOI <https://doi.org/10.1007/3-540-47721-7_12>`__.

1987 -- Feldman's Verifiable Secret Sharing
-------------------------------------------

In Shamir's scheme everyone must trust the dealer who hands out the shares: a
dishonest dealer can hand out points that lie on no common polynomial, and
nobody notices until recovery fails. Paul Feldman made the shares checkable
without interaction. The dealer publishes :math:`C_j = g^{a_j}` for each
polynomial coefficient (with :math:`a_0 = s`), and share holder :math:`i`
checks

.. math::

   g^{f(i)} = \prod_{j=0}^{t-1} C_j^{\,i^{j}} \pmod p.

Exponentiation turns sums into products, so the right side equals
:math:`g^{\sum_j a_j i^j} = g^{f(i)}`. Because :math:`g` has prime order
:math:`q`, the check passes exactly when the share equals :math:`f(i)` modulo
:math:`q`, that is, when it lies on the committed polynomial. The price is
that :math:`C_0 = g^{s}` is public, so the secret is protected only by the
hardness of the discrete log rather than information-theoretically.
Verifiable sharing underlies distributed key generation, which threshold
wallets use to create a key that no single party ever holds.

*Implementation:* :func:`blockchainkit.crypto.systems.sharing.feldman_split` and
:func:`blockchainkit.crypto.systems.sharing.feldman_verify` work over
:data:`blockchainkit.crypto.systems.asymmetric.TEACHING_GROUP`, where discrete
logs are easy to compute. Real verifiable secret sharing needs a group of
cryptographic size and a broadcast channel for complaints.

*References:* P. Feldman, *A Practical Scheme for Non-interactive Verifiable
Secret Sharing*, 28th Symposium on Foundations of Computer Science (FOCS),
427–438 (1987). `DOI <https://doi.org/10.1109/SFCS.1987.4>`__.

1989 -- The Merkle-Damgård Construction and Length Extension
------------------------------------------------------------

A hash function must accept messages of any length, but it is much easier to
design and analyze a *compression function* :math:`f` that maps a fixed-size
state and one fixed-size block to a new state. Ralph Merkle and Ivan Damgård
independently showed at CRYPTO '89 how to chain one: pad the message with its
length, split it into blocks, and feed each block through :math:`f`; the final
state is the digest:

.. math::

   h_0 = IV, \qquad h_i = f(h_{i-1}, m_i), \qquad H(m) = h_\ell.

If :math:`f` is collision-resistant, so is :math:`H`. Trace two colliding
messages backward from their equal digests: at the last step where the inputs
to :math:`f` differ, the outputs are still equal, which is a collision in
:math:`f`. The encoded length guarantees that such a step exists. MD5, SHA-1
and SHA-256 all follow this design. Its side effect: since :math:`H(m)` *is*
the chaining state, anyone can resume the chain from it and compute
:math:`H(m \,\|\, \text{pad} \,\|\, s)` knowing only :math:`H(m)` and
:math:`|m|`. A "MAC" computed as :math:`H(k \,\|\, m)` is therefore forgeable:
from one valid tag an attacker can tag an extended message without knowing
:math:`k`.

*Implementation:* :func:`blockchainkit.crypto.systems.merkle_damgard.merkle_damgard_sha256`
reimplements SHA-256 block by block (checked against the standard library);
:func:`blockchainkit.crypto.systems.merkle_damgard.length_extension` performs
the attack.

*References:* R. C. Merkle, *One Way Hash Functions and DES*, CRYPTO '89, LNCS
435, 428–446 (1990). `DOI <https://doi.org/10.1007/0-387-34805-0_40>`__. I. B.
Damgård, *A Design Principle for Hash Functions*, CRYPTO '89, LNCS 435, 416–427
(1990). `DOI <https://doi.org/10.1007/0-387-34805-0_39>`__.

1989-1991 -- Schnorr Identification and Compact Signatures
----------------------------------------------------------

Claus Schnorr made discrete-log proofs short and fast. In additive notation, a
prover with secret :math:`x` and public key :math:`Q = xG` commits with a
fresh nonce :math:`k`, then answers a challenge :math:`c`. The verifier's
check holds because :math:`sG = (k + cx)G = kG + c(xG)`:

.. math::

   R=kG,\qquad s=k+cx\pmod n,\qquad sG=R+cQ.

The Fiat-Shamir transform with :math:`c = H(R, Q, m)` turns this into a
signature :math:`(R, s)`: one group element and one scalar. The nonce must be
fresh, since two signatures with the same :math:`k` give two linear equations
in :math:`k` and :math:`x` (the 2010-2013 entry). The equation is also linear
in the keys: if two signers use the same :math:`c`, their :math:`R` and
:math:`s` values add to a valid signature for :math:`Q_1 + Q_2`, which later
enabled multi-signatures (the 2018 entry). A patent kept Schnorr signatures
out of standards until it expired in 2008; Bitcoin adopted them in 2021 as
BIP-340.

*Implementation:* :func:`blockchainkit.crypto.systems.signatures.sign`,
:func:`blockchainkit.crypto.systems.signatures.verify`, and
:func:`blockchainkit.crypto.systems.signatures.recover_reused_nonce_key` use a
domain-separated scheme over a prime-order elliptic-curve group, an additive
adaptation of the original multiplicative groups. The challenge encoding
differs from BIP-340 (no x-only keys or tagged hash), so these signatures do
not verify in Bitcoin.

*References:* C. P. Schnorr, *Efficient Signature Generation by Smart Cards*,
Journal of Cryptology 4, 161–174 (1991); following the CRYPTO '89 work. `DOI
<https://doi.org/10.1007/BF00196725>`__.

1991 -- Pedersen Commitments: Perfectly Hiding and Additive
-----------------------------------------------------------

A hash commitment hides its contents only from an attacker who cannot invert
the hash, and nothing useful can be computed on sealed values. Torben Pedersen
introduced a commitment that hides its contents even from an attacker with
unlimited computing power, and where multiplying sealed commitments adds the
amounts inside them. With two generators :math:`g, h` of a group of prime
order :math:`q`:

.. math::

   C(v, r) = g^{v} h^{r} \bmod p, \qquad C(a, r)\,C(b, s) = C(a + b,\ r + s).

Write :math:`h = g^{w}`. Then :math:`C = g^{v + wr}`, and for any other value
:math:`v'` the blinding :math:`r' = r + (v - v')/w \bmod q` gives the same
:math:`C`. Every value is equally consistent with :math:`C`, so hiding is
perfect. Conversely, anyone who opens one commitment to two values
:math:`(v, r) \ne (v', r')` has :math:`v + wr = v' + wr'` and can solve for
:math:`w = \log_g h`. Binding is therefore only as strong as that discrete
log, which is why :math:`h` is derived by hashing, so that nobody knows
:math:`w`. The additive property lets anyone check that hidden inputs equal
hidden outputs: the basis of confidential transactions in Monero and
Mimblewimble.

*Implementation:* :func:`blockchainkit.crypto.systems.commitments.pedersen_commit`
and :func:`blockchainkit.crypto.systems.commitments.pedersen_generators` work in
the teaching group, so binding holds only while its small discrete logarithm
stays unknown; production uses 256-bit elliptic-curve groups.

*References:* T. P. Pedersen, *Non-Interactive and Information-Theoretic Secure
Verifiable Secret Sharing*, CRYPTO '91, LNCS 576, 129–140 (1992). `DOI
<https://doi.org/10.1007/3-540-46766-1_9>`__.

1996 -- HMAC: Keyed Hashing Done Right
--------------------------------------

To prove that a message came from someone holding a shared key, the key must
be mixed into the hash in a way that leaves an attacker nothing to extend; the
1989 entry shows that :math:`H(k \,\|\, m)` fails this test. Bellare, Canetti
and Krawczyk defined HMAC, which hashes twice with two keys derived from
:math:`k`, and proved it secure under assumptions about the compression
function:

.. math::

   \mathrm{HMAC}(k, m) = H\bigl((k \oplus opad) \,\|\, H((k \oplus ipad) \,\|\, m)\bigr).

Length extension now fails. Resuming the outer hash from the tag only appends
data after the inner digest. A tag for :math:`m \,\|\, s` needs the inner
digest of :math:`m \,\|\, s`, which the attacker cannot compute without the
key. HMAC became RFC 2104 in 1997 and is everywhere: TLS, key derivation
(HKDF), and the deterministic nonces of RFC 6979.

*Implementation:* :func:`blockchainkit.crypto.systems.mac.hmac_sha256`,
contrasted with the broken :func:`blockchainkit.crypto.systems.mac.naive_mac`.

*References:* M. Bellare, R. Canetti, and H. Krawczyk, *Keying Hash Functions
for Message Authentication*, CRYPTO '96, LNCS 1109, 1–15 (1996). `DOI
<https://doi.org/10.1007/3-540-68697-5_1>`__.

2002 -- SHA-256 as a Standardized Hash Primitive
------------------------------------------------

Different programs must compute the same fingerprint for the same data, or a
signature made by one cannot be checked by another. NIST's FIPS 180-2
specified SHA-256 alongside other secure hash algorithms, with test vectors
that independent implementations can check themselves against. A good hash
behaves like a random function, so related inputs must give unrelated
outputs: changing one input bit should flip each of the 256 output bits
independently with probability one half (the *avalanche* effect). The number
of flipped bits is then binomial:

.. math::

   d = \mathrm{popcount}\bigl(H(m) \oplus H(m')\bigr)
   \sim \mathrm{Binomial}\bigl(256, \tfrac12\bigr), \qquad
   E[d] = 128, \quad \sigma_d = 8.

If outputs clustered by input instead, an attacker could steer toward a
target digest faster than the :math:`2^{256}` (preimage) or :math:`2^{128}`
(collision, the 1979 entry) work that a random function forces. A digest is a
compact fingerprint; it does not encrypt the input, and a guessable input can
be found by hashing candidates.

*Implementation:* :func:`blockchainkit.crypto.systems.hashing.sha256` delegates
to Python's standard library;
:func:`blockchainkit.crypto.systems.merkle_damgard.merkle_damgard_sha256` is a
readable reimplementation (the 1989 entry) that the tests check against it.

*References:* NIST, *Secure Hash Standard*, FIPS PUB 180-2 (2002). `Historical
standard record <https://csrc.nist.gov/pubs/fips/180-2/final>`__, cited for
historical context rather than as current standards guidance.

2010-2013 -- Nonce Reuse in Practice, and Deterministic Nonces
--------------------------------------------------------------

A signature hides the private key behind a fresh random nonce. With
:math:`s_i = k + c_i x`, two signatures that share :math:`k` but sign
different messages (so :math:`c_1 \ne c_2`) are two linear equations in two
unknowns. Subtracting them eliminates :math:`k`:

.. math::

   s_1 - s_2 = (c_1 - c_2)\,x
   \quad\Longrightarrow\quad
   x = \frac{s_1 - s_2}{c_1 - c_2} \bmod n.

ECDSA's equation is different, :math:`s = k^{-1}(z + rx)`, but the same
counting applies: a repeated nonce leaves two equations in :math:`k` and
:math:`x`. In December 2010 the fail0verflow team showed that Sony's
PlayStation 3 signed software with a constant ECDSA nonce, and recovered
Sony's private key. Weak random number generators in Android wallets led to
Bitcoin thefts in 2013. The fix was to stop needing randomness: Thomas
Pornin's RFC 6979 derives the nonce from an HMAC-based deterministic generator
seeded with the private key and the message hash. Distinct messages get
distinct nonces, so the equations above never arise, and the nonce is
unpredictable without the key.

*Implementation:* :func:`blockchainkit.crypto.systems.signatures.recover_reused_nonce_key`
performs the extraction;
:func:`blockchainkit.crypto.systems.signatures.deterministic_nonce` implements
RFC 6979 section 3.2 with SHA-256 and reproduces the RFC's test vectors. It
feeds this package's Schnorr signatures rather than ECDSA, and adds no
protection against fault attacks.

*References:* fail0verflow (bushing, marcan, sven), *Console Hacking 2010: PS3
Epic Fail*, 27th Chaos Communication Congress (2010). T. Pornin,
*Deterministic Usage of the Digital Signature Algorithm (DSA) and Elliptic
Curve Digital Signature Algorithm (ECDSA)*, RFC 6979 (2013). `DOI
<https://doi.org/10.17487/RFC6979>`__.

2018 -- MuSig: Schnorr Multi-Signatures and the Rogue-Key Attack
----------------------------------------------------------------

Schnorr signatures are linear, so with a shared challenge :math:`c`, partial
signatures :math:`s_i = k_i + c x_i` add up to one ordinary signature for the
aggregate key :math:`\sum Q_i` and nonce :math:`\sum R_i`. Done naively, the
last signer to announce a key can wait for the others and announce
:math:`Q_{\text{rogue}} = xG - Q_{\text{honest}}` for an :math:`x` they know.
They do not know the private key of :math:`Q_{\text{rogue}}`, but they do not
need it: the aggregate is :math:`xG`, so they can sign alone. Maxwell,
Poelstra, Seurin and Wuille's MuSig weights every key by a hash of the whole
key list :math:`L`:

.. math::

   a_i = H(L, Q_i), \qquad Q_{\text{agg}} = \sum_i a_i Q_i, \qquad
   s = \sum_i (k_i + c\, a_i x_i).

The cancellation needs a key chosen as a function of the others' weighted
keys, but the weights depend on the attacker's own key through :math:`L`.
Changing the key changes every coefficient unpredictably, so the attacker is
left guessing, as with any hash. Bitcoin's Taproot upgrade (2021) made such
aggregate spends indistinguishable from single-signer spends.

*Implementation:* :func:`blockchainkit.crypto.systems.multisig.musig_coefficients`,
:func:`blockchainkit.crypto.systems.multisig.aggregate_public_keys`, and
:func:`blockchainkit.crypto.systems.multisig.musig_sign`. All signers run in
one process; real MuSig needs a round of nonce commitments (or MuSig2's two
nonces per signer) to resist attacks across concurrent signing sessions.

*References:* G. Maxwell, A. Poelstra, Y. Seurin, and P. Wuille, *Simple
Schnorr Multi-Signatures with Applications to Bitcoin*, Designs, Codes and
Cryptography 87, 2139–2164 (2019); preprint IACR ePrint 2018/068. `DOI
<https://doi.org/10.1007/s10623-019-00608-x>`__.
