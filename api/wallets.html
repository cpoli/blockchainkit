blockchainkit.wallets#

blockchainkit.wallets hub · History · Examples · API reference

Wallets: keys as users actually hold them.

Error-detecting codes behind addresses, from BCH codes and Verhoeff’s check digit to Base58Check, Bech32 and Bech32m; key stretching with PBKDF2 and scrypt, and the brain wallets that had none; hierarchical deterministic keys, mnemonic seed phrases and derivation paths; and shared control of keys, from pay-to-script-hash multisig and threshold ECDSA to social-recovery wallets and ERC-4337 account abstraction.

Keys as users actually hold them: check digits and the error-detecting codes behind Base58Check, Bech32 and Bech32m addresses; PBKDF2 and scrypt, and the brain wallets that used neither; BIP32 key trees, BIP39 seed phrases and BIP44 paths; and shared control, from P2SH multisig and threshold ECDSA to social recovery and ERC-4337 accounts.

Every public name below is re-exported by the subpackage: import it as bk.wallets.<name>. The utilities and the plotting helpers are the exceptions: import them from blockchainkit.wallets.utils and blockchainkit.wallets.visualizers, which loads Matplotlib.

BCH codes (Hocquenghem, 1959; Bose and Ray-Chaudhuri, 1960).

A binary BCH code of length n = 2**m - 1 treats a word of n bits as a polynomial over GF(2) and accepts exactly the multiples of a generator g(x) chosen to vanish at alpha, alpha**2, …, alpha**(2t) in GF(2**m). Any nonzero codeword then has at least 2t + 1 nonzero bits (the BCH bound), so up to t flipped bits are corrected and up to 2t detected. Decoding computes the syndromes S_j = r(alpha**j), finds the error-locator polynomial with the Berlekamp-Massey algorithm, and finds its roots by trying every position (Chien’s search).

Bech32’s checksum is a BCH code too, over GF(32) rather than GF(2): see blockchainkit.wallets.systems.bech32.

BCHDecoding

Check digits: Luhn’s (1954) and Verhoeff’s (1969).

A check digit is appended so that a number typed with a mistake fails a test. Verhoeff’s study of Dutch post-office data found that single wrong digits and swaps of two adjacent digits make up most typing errors (about 80% and 10%). A sum modulo 10 catches every single error but no swap, because addition commutes. Luhn’s scheme, used on payment cards, doubles every second digit, which catches every swap but one: 09 and 90.

Verhoeff’s scheme catches them all, by computing in a group that does not commute: the dihedral group D5 of the ten symmetries of a pentagon, with the digits 0-4 as rotations and 5-9 as reflections. Digit i (counting from the right, check digit at i = 0) is first permuted by \(\sigma^i\), where \(\sigma\) is a fixed permutation, and the number is valid when the product is the identity:

\[\sigma^{0}(a_0) * \sigma^{1}(a_1) * \cdots * \sigma^{k}(a_k) = 0 .\]

Base58Check addresses (Nakamoto, 2009).

A Bitcoin address is a version byte and the 20-byte HASH160 of a public key, followed by a 4-byte checksum, the first bytes of SHA256(SHA256(version || payload)), and written in base 58. The alphabet leaves out 0, O, I and l, which look alike, and every leading zero byte becomes a leading 1. A mistyped address fails the checksum unless the typo happens to match it, with probability

\[2^{-32} \approx 2.3 \times 10^{-10},\]

so a wallet refuses to pay it. The checksum detects errors but cannot say where they are. blockchainkit.structures names accounts by a bare SHA-256 hex digest, where every typo is another valid address.

Bech32 addresses (Wuille and Maxwell, BIP173, 2017) and Bech32m (Wuille, BIP350, 2020).

A Bech32 string is a human-readable part such as bc, the separator 1, and data in 32 lower-case characters chosen to avoid look-alikes, ending in a 6-character checksum. The checksum is a BCH code over GF(32): the data and checksum, read as a polynomial with 5-bit coefficients, must leave a fixed remainder modulo a generator g(x) of degree 6,

\[\mathrm{polymod}(\mathrm{expand}(hrp) \,\|\, data \,\|\, checksum) = 1 .\]

g(x) was chosen by a search of 159,605 BCH codes for the best detection of the errors people make: every error affecting at most 4 characters is detected in strings of up to 89 characters, which Base58Check’s 32-bit hash cannot promise.

In 2019 a weakness was found: when a string ends in p, inserting or deleting q characters just before it leaves the checksum valid, because q is the value 0 and the constant 1 lets the polynomial absorb factors of x. Segregated-witness version 0 survives, since its programs must be 20 or 32 bytes, but later versions allow other lengths. Bech32m changes only the constant, to 0x2bc830a3, and is required from witness version 1 (Taproot) on.

Key stretching#

PBKDF2 key stretching (Kaliski, RFC 2898, 2000).

A key derived from a password is only as hard to guess as the password. Stretching cannot add entropy, but it can make every guess expensive: PBKDF2 iterates a keyed hash c times, so an attacker trying N passwords pays about N * c hash calls instead of N, while the honest user pays c once. A random salt, mixed into the first iteration, stops one precomputed table from serving every user. Block i of the output is

\[T_i = U_1 \oplus U_2 \oplus \cdots \oplus U_c, \quad U_1 = \mathrm{PRF}(P, S \,\|\, \mathrm{INT}(i)), \quad U_j = \mathrm{PRF}(P, U_{j-1}),\]

with HMAC as the pseudorandom function PRF. BIP39 uses PBKDF2 with HMAC-SHA512 and 2048 iterations to turn a mnemonic into a seed.

scrypt, a sequential memory-hard key derivation function (Percival, 2009).

PBKDF2 makes each guess slow, but a guess needs almost no memory, so an attacker with custom chips runs millions of guesses side by side. scrypt makes each guess need a large table as well. ROMix fills a table V of N blocks, each the BlockMix of the last, then makes N reads at addresses that depend on the data:

\[V_i = \mathrm{BlockMix}^{\,i}(B), \qquad X \leftarrow \mathrm{BlockMix}(X \oplus V_{\mathrm{Integerify}(X) \bmod N}).\]

An attacker can store fewer entries and recompute the missing ones, but keeping only every k-th entry multiplies the second loop’s work by about (k + 1)/2: memory times time stays roughly constant. Percival proved that no algorithm does much better, so the cost of an attack in chip area and time grows with N squared. BlockMix is built from the Salsa20/8 core. This module implements RFC 7914 exactly, and romix() adds the trade-off.

Brain wallets and the thieves who drain them (Vasek et al., 2016).

A brain wallet keeps no file: its private key is the SHA-256 of a passphrase the owner remembers,

\[k = \mathrm{SHA256}(\text{passphrase}),\]

so the coins can be carried in one’s head across a border. But anyone can compute the same key. Thieves hash dictionaries, quotations, song lyrics and leaked passwords, keep a table from address to key, and watch the chain: when a deposit reaches an address in the table, they move the coins away. Vasek et al. searched the Bitcoin chain for such addresses, found hundreds of funded brain wallets, and found that most were emptied, many within minutes of their first deposit, by thieves racing one another. The passphrase has the entropy a person chooses, not the 128 bits a random key has, and there is no salt and no stretching to slow the thieves down.

Key derivation#

Hierarchical deterministic wallets (Wuille, BIP32, 2012).

Early wallets drew every key at random, so a backup was stale as soon as the next key was made. BIP32 derives a whole tree of secp256k1 keys from one seed. An extended key is a key k with a 32-byte chain code c, and child i comes from

\[I = \mathrm{HMAC\text{-}SHA512}(c,\ \mathrm{data}), \qquad k_i = I_L + k \bmod n, \qquad c_i = I_R,\]

where the data is the parent’s compressed public key and i for a normal child, or the private key and i for a hardened child, i >= 2**31. Because \(k_i G = I_L G + K\), a normal child’s public key follows from the parent’s public key alone: a shop can hold the extended public key and make a fresh address for every order, with no private key on its server.

The price is that the extended public key and any one normal child’s private key reveal the parent’s private key, \(k = k_i - I_L\). Hardened children cut that link, which is why account keys are hardened.

Mnemonic seed phrases (Palatinus, Rusnak, Voisine and Bowe, BIP39, 2013).

A 128-bit seed written in hexadecimal is 32 characters that people miscopy. BIP39 writes it as words instead. The entropy gets a checksum, its first ENT/32 bits of SHA-256, and the bits are cut into 11-bit groups, each an index into a list of 2048 words:

\[\text{words} = \frac{ENT + ENT/32}{11}, \qquad 128 \text{ bits} \to 12 \text{ words}.\]

A mistyped word is caught by the checksum unless the bits happen to match, which for 12 words is 1 time in 16. The phrase then goes through PBKDF2-HMAC-SHA512 with 2048 iterations, salted with "mnemonic" and an optional passphrase, to give the 64-byte seed for BIP32. Every passphrase gives a valid, different wallet, so a passphrase cannot be checked: a forgotten one and a decoy look the same.

Teaching difference: the word list is not BIP39’s English list but 2048 four-letter words generated by a rule (consonant, vowel, consonant, vowel), in sorted order, so that index and word convert without a stored list. mnemonic_to_seed() takes any phrase, so it reproduces BIP39’s published seeds for English phrases.

Multi-account derivation paths (Palatinus and Rusnak, BIP44, 2014).

BIP32 allows any tree; for one seed to restore the same wallet in another program, the programs must agree on where keys sit. BIP44 fixes five levels,

Shared control#

Pay to script hash (Andresen, BIP16, 2012) and multisig wallets.

Before 2012, a coin locked by several keys carried the whole locking script, so the payer had to know and pay for the payee’s security policy. P2SH locks a coin to the hash of a redeem script instead:

\[\text{locking} = \texttt{OP\_HASH256}\ \langle H(\text{redeem}) \rangle\ \texttt{OP\_EQUAL}\]

The spender reveals the redeem script as the last push of the unlocking script. Validation runs twice: first the unlocking script and the locking script, which only check the hash; then, if that passes, the redeem script on the stack the unlocking script left, which checks the signatures. The payer sees only a 20-byte hash in a short address starting with 3, and the policy, such as 2 of 3 keys, stays private until the coin is spent.

Teaching differences from BIP16: the hash is OP_HASH256 (double SHA-256), because blockchainkit.vm.systems.script has no OP_HASH160; and since it has no OP_CHECKMULTISIG either, an m-of-n redeem script is a tree of OP_IF branches, one per set of m signers, which the spender picks with true and false pushes. Its size grows like C(n, m), so the 520-byte limit on a pushed script soon binds: 2-of-3 fits, 3-of-5 does not.

ECDSA on secp256k1, the signature scheme Bitcoin and Ethereum use for accounts.

A signature on message hash z with key x and nonce k is

\[R = kG, \qquad r = R_x \bmod n, \qquad s = k^{-1}(z + r x) \bmod n,\]

and it verifies when \((z s^{-1}) G + (r s^{-1}) Q\) has x coordinate r. Unlike Schnorr’s \(s = k + c x\), the response multiplies the secret nonce’s inverse by the key, so signatures by several parties do not simply add: see blockchainkit.wallets.systems.threshold. Nonces come from RFC 6979 by default, and s is normalized to the lower half of [1, n), as Bitcoin requires since BIP146 to stop third parties from changing a transaction’s ID by negating s.

Threshold ECDSA (Gennaro and Goldfeder, 2018).

A multisig script shows its policy on chain and costs one signature per signer. A threshold signature is a single ordinary signature under a single key, made by any t of n parties who each hold a Shamir share of a private key that nobody ever computes. For Schnorr this is easy, since responses add. ECDSA’s \(s = k^{-1}(z + r x)\) multiplies secrets, so the parties need products of values that are split between them.

Gennaro and Goldfeder’s protocol gets them with a two-party multiplicative-to-additive (MtA) conversion: parties holding a and b end with \(\alpha + \beta = ab\) without revealing a or b. With nonce shares \(k_i\), masks \(\gamma_i\) and Lagrange-weighted key shares \(w_i\), MtA gives additive shares of \(\delta = k\gamma\) and \(\sigma = kx\). Revealing \(\delta\) leaks nothing, because \(\gamma\) hides \(k\), and

\[R = \delta^{-1} \sum_i \gamma_i G = k^{-1} G, \qquad s = \sum_i (z k_i + r \sigma_i) = k (z + r x),\]

which is an ECDSA signature with nonce \(k^{-1}\).

Teaching difference: the key is generated jointly with Feldman commitments on secp256k1, but multiplicative_to_additive() is an ideal functionality, a function that splits the product at random. The real protocol runs MtA with Paillier encryption and zero-knowledge range proofs, so that no party learns another’s inputs, and it checks every step to catch a cheating party.

Social-recovery wallets (Buterin, 2021).

A single seed phrase is a single point of failure twice over: lose it and the coins are gone, let it be copied and they are stolen. A social-recovery wallet is a contract with one signing key for daily use and a set of guardians, friends, devices or institutions, any m of whom can replace the signing key. The owner need back up nothing, and a thief with the signing key alone can be locked out by the guardians.

With n guardians, each independently lost with probability \(p_l\) or corrupt with probability \(p_c\), recovery fails when fewer than m are honest, and the wallet is stolen when m are corrupt:

\[P(\text{theft}) = \sum_{j \ge m} \binom{n}{j} p_c^{\,j} (1 - p_c)^{n-j} .\]

Raising m trades theft for lockout. Changing the guardians is delayed, so a thief who takes the signing key cannot replace them before they act.

Teaching differences: guardians are accounts that send transactions, not signatures collected off chain, and the wallet holds only ether.

Account abstraction without a consensus change (Buterin et al., ERC-4337, 2021).

On Ethereum an account is either a key pair, which can start transactions but whose rules are fixed (one ECDSA key, pay gas in ether), or a contract, whose rules are code but which cannot start a transaction. ERC-4337 lets a contract account act like a key pair without changing the protocol. The owner signs a user operation and sends it to an alternative mempool. A bundler collects operations and submits them in one ordinary transaction to a singleton EntryPoint contract, which for each operation

  1. asks the account to validate it, checking the signature and nonce by whatever rule the account’s code chooses, and to pay its fee;

  2. then runs it, and pays the bundler the fees collected.

A failing validation reverts the whole bundle, at the bundler’s cost, so a bundler first simulates each operation on a copy of the state and drops those that fail. A failing execution only marks its operation failed: the fee is still paid. The account’s rule can be anything: key rotation, multisig, social recovery, session keys, or another signature scheme. The operation hash binds the EntryPoint and the chain,

\[h = \mathrm{SHA256}(\text{domain} \,\|\, \text{EntryPoint} \,\|\, \text{chain} \,\|\, \text{operation}),\]

so a signed operation cannot be replayed elsewhere.

Teaching differences: the fee is a fixed amount rather than gas used times a gas price, there are no paymasters, aggregators or factories, accounts sign with this package’s Schnorr signatures, and the validation-phase restrictions on storage access are not enforced.
