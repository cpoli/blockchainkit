blockchainkit.privacy#

blockchainkit.privacy hub · History · Examples · API reference

Privacy: anonymity and confidentiality on public ledgers.

A public ledger is a permanent record of who paid whom. This subpackage measures what it reveals, by clustering addresses, tracing ring inputs and counting anonymity sets, and builds the techniques that hide senders, receivers and amounts: mix-nets and onion routing, CoinJoin, ring signatures and key images, stealth addresses, Zerocoin, confidential transactions, RingCT, Mimblewimble, TumbleBit, and a Tornado Cash-style mixer contract.

Anonymity and confidentiality on public ledgers: what a ledger reveals, measured by anonymity sets, address clustering and ring tracing, and the techniques that hide senders, receivers and amounts, from mix-nets and ring signatures to confidential transactions, Mimblewimble and a mixer contract.

Every public name below is re-exported by the subpackage: import it as bk.privacy.<name>. The plotting helpers are the exception: import them explicitly from blockchainkit.privacy.visualizers, which loads Matplotlib.

Anonymous networks and anonymity sets#

Chaum’s mix-nets: untraceable mail from layered encryption and shuffling (1981).

A sender who wants to hide who it writes to encrypts its message for the recipient, then for the last mix, then for the one before, like nested envelopes. Each mix removes one layer, which tells it only the next hop. It collects a batch of messages, removes their layers, and sends them on in a random order. An observer of every wire sees messages go in and come out, but the layers change their bytes and the shuffle changes their order, so it cannot match them. One honest mix in the cascade is enough.

Each layer here is hashed ElGamal in the teaching group: a fresh R = g**k, and the plaintext XORed with a keystream from the shared R**x = X**k. Chaum used RSA and padded every message to one length; these layers grow by the hop name and 8 bytes each.

Onion routing in Tor: low-latency anonymity and its end-to-end weakness (2004).

Tor wraps traffic in layers as a mix-net does, through a circuit of three relays: an entry guard, a middle relay and an exit. Each relay learns only its neighbours on the circuit. Unlike a mix, a relay forwards each packet at once, without batching or reordering, so web browsing stays fast. The price, which Dingledine, Mathewson and Syverson state in the design, is that an adversary watching both the entry and the exit of a circuit can match the timing of what goes in to what comes out. If it runs a fraction f of the relays, about f**2 of circuits are exposed.

The circuit itself reuses wrap(); real Tor builds circuits by telescoping Diffie-Hellman handshakes and then sends fixed 512-byte cells under symmetric keys.

k-anonymity and anonymity sets: how many people a record could belong to (2002).

Sweeney showed that a ZIP code, a birth date and a sex, released without names, still single out most Americans: joined with a voter list, they named the Governor of Massachusetts in “anonymous” hospital records. A table is k-anonymous if every combination of those quasi-identifiers is shared by at least k rows, so each person hides among k.

The same year, Serjantov and Danezis, and Díaz, Seys, Claessens and Preneel, measured anonymity on networks the same way: by the anonymity set of possible senders. Counting the set overstates it when an attacker finds some members likelier than others, so they weighted it by the Shannon entropy of the attacker’s guess: \(2^{H}\) equally likely senders give the same uncertainty.

Ring signatures and stealth addresses#

Ring signatures: signing for a group chosen on the spot (Rivest, Shamir and Tauman, 2001).

A ring signature convinces anyone that one of the listed public keys signed, without revealing which. Unlike a group signature there is no manager and no setup: the signer picks the other members’ public keys itself, and they need not know. The signature is a closed ring of challenges: each member’s challenge is the hash of the previous member’s commitment, and the signer’s secret key is what lets it close the ring.

For keys \(y_i = g^{x_i}\) and signer \(s\), the signer picks \(u\) and starts the ring at \(c_{s+1} = H(m, g^u)\); every other member gets a random response \(r_i\) and \(c_{i+1} = H(m, g^{r_i} y_i^{c_i})\). Only the signer can then answer \(r_s = u - x_s c_s\), which makes \(g^{r_s} y_s^{c_s} = g^u\).

This is the discrete-log construction of Abe, Ohkubo and Suzuki (2002), which Monero’s signatures descend from. Rivest, Shamir and Tauman built their ring from RSA trapdoor permutations and a symmetric cipher.

Linkable ring signatures and key images: anonymous, but only once (Liu, Wei and Wong, 2004).

A ring signature hides the spender, so on its own it would let a coin be spent twice: two signatures by the same key look unrelated. A linkable ring signature adds a key image \(I = H_p(P)^x\), a value fixed by the signer’s key \(P = g^x\) but not revealing it. Every signature by that key carries the same image, so the ledger rejects the second spend, yet nobody learns which ring member made either one.

The ring proves both statements with the same response, for each member \(i\) with challenge \(c_i\) and response \(r_i\):

\[L_i = g^{r_i} P_i^{c_i}, \qquad R_i = H_p(P_i)^{r_i} I^{c_i}, \qquad c_{i+1} = H(m, L_i, R_i).\]

Only the signer can close the ring with a single \(x\) that serves both. MLSAG (Noether, 2016) signs with one key per column for each member at once, the same challenge chaining them; RingCT uses a second column to prove amounts balance.

The key image here hashes the public key, as CryptoNote does, so it links signatures across different rings; Liu, Wei and Wong hashed the ring, which links only signatures over the same ring.

Stealth addresses: one published address, a fresh key for every payment (CryptoNote, 2013).

Reusing an address links every payment to it; asking each payer for a new one needs a conversation. CryptoNote, the protocol behind Monero, lets the payer derive a fresh one-time key from a single published address \((A, B) = (g^a, g^b)\). The payer picks \(r\), publishes \(R = g^r\) with the transaction, and pays to

\[P = g^{H(A^r)} B .\]

Only the payee can recognise it, since \(A^r = R^a\) needs either \(r\) or \(a\), and only the payee can spend it, with the key \(x = H(R^a) + b\). The view key \(a\) alone finds incoming payments without being able to spend them, so it can be handed to an auditor. To everyone else, the outputs paid to one address look unrelated.

CryptoNote hashes the output’s index in the transaction along with \(R^a\); here the index is an argument, 0 by default.

Tracing a ledger#

Address clustering: grouping a ledger’s addresses by owner (Meiklejohn et al., 2013).

Bitcoin users hide behind fresh addresses, but how they spend gives them away. A Fistful of Bitcoins clustered addresses with two heuristics:

  • Common input ownership. A transaction’s inputs are signed by their owners together, so every input address of one transaction belongs to one user (Nakamoto noted it in the white paper).

  • One-time change. A wallet sends the change back to a fresh address. If exactly one output address of a transaction has never appeared before, and no input address reappears among the outputs, that output is the change and belongs to the sender too.

Labelling a few clusters, by buying from a service or depositing at an exchange, then names every address in them.

simulate_payments() makes a toy economy with known owners; real wallets select coins and create change in many more ways, which is where the change heuristic makes its mistakes.

Traceability in Monero: how decoys fail (Möser et al.; Kumar et al., 2018).

A Monero input hides its real output among decoys (mixins) drawn from earlier outputs. Two studies in 2017-2018 found that, in practice, most inputs up to 2017 could be traced:

  • Zero-mixin chain reaction. Until 2016 Monero allowed rings with no decoys. Such an input reveals the output it spends; that output can then be struck from every other ring that uses it as a decoy, which may leave some of those rings with one member, and so on. Möser et al. could deduce the real output of most inputs made before 2017 this way.

  • Guess-newest. People tend to spend coins soon after receiving them, but decoys were drawn uniformly from all past outputs, so most of them were old. The newest member of a ring was the real one about 80% of the time.

Monero’s fixes were a minimum ring size (2016, raised to 11 in 2018) and drawing decoys from a distribution fitted to real spending ages. In simulate_rings() an output’s index is its age order, and real spends and "recent" decoys share one geometric age distribution.

Mixing coins#

CoinJoin: many payers in one transaction, so its inputs need not share an owner (2013).

Gregory Maxwell pointed out on the Bitcoin forum that nothing requires a transaction’s inputs to belong to one person. Several users can each contribute an input and name an output, check the joint transaction, and sign only their own input. If every mixed output pays the same denomination, an observer cannot tell whose output is whose: for \(n\) such outputs each user hides among \(n\), and the common input ownership heuristic, applied to the transaction, merges strangers.

The change outputs are another matter. Each one is an input amount minus the denomination, which usually links it to its input, so only the equal-valued outputs are anonymous.

coinjoin() builds the transaction without fees or signatures; real rounds (JoinMarket, Wasabi, Whirlpool) coordinate through a server or a market and use blinded registrations so the coordinator cannot link inputs to outputs either.

TumbleBit: an untrusted payment hub that cannot link payers to payees (Heilman et al., 2017).

A tumbler mixes coins by receiving from payers and paying payees. A centralised mixer can steal and can see who paid whom. TumbleBit removes both risks with RSA puzzles. For each payee the tumbler issues a promise: a puzzle \(z = \\epsilon^{e} \bmod N\) and its payment token encrypted under \(\\epsilon\). Only the tumbler, with its RSA secret, can solve the puzzle. The payee blinds the puzzle,

\[\begin{split}z' = z \\cdot \rho^{e} \bmod N ,\end{split}\]

and gives \(z'\) to a payer, who pays the tumbler to solve it. The tumbler returns \(\\epsilon \rho\), the payer passes it on, and the payee divides by \(\rho\) to get \(\\epsilon\) and open its token. The tumbler saw \(z\) with the payee and \(z'\) with the payer, which are unrelated numbers to it: the same blinding as Chaum’s blind signatures.

TumbleBit makes each step a fair exchange on chain, with hash-locked escrows and cut-and-choose, so the tumbler cannot take a payment without solving the puzzle or promise a token it does not deliver. This model keeps only the puzzles and blinding, and the token is a byte string.

Tornado Cash: a mixer contract with zero-knowledge withdrawals (2019).

Tornado Cash put Zerocash’s notes and nullifiers in an Ethereum contract. A user deposits a fixed amount, say 1 ether, together with the commitment to a secret note; the contract appends it to a Merkle tree of deposits. Later, from a fresh address, anyone holding the note withdraws by publishing its nullifier and a zk-SNARK proving the note is a leaf under a recent root. The contract pays out once per nullifier. Because all deposits are the same size, the withdrawal could be any earlier deposit not yet withdrawn: that is the anonymity set.

The proof hides the link, but behaviour does not. Users who withdraw to the address they deposited from, or withdraw right after an unusual deposit, shrink their anonymity sets to one. In August 2022 the US Treasury sanctioned the Tornado Cash contracts, after hackers had laundered stolen funds through them.

This mixer proves with the Zerocash spend circuit of blockchainkit.proofs (Groth16 over a toy pairing, MiMC hashing). The circuit’s new-note commitment is used to bind the recipient: it must be the commitment to a zero-valued note “owned” by the recipient’s tag, so a front-runner cannot redirect a withdrawal. Tornado binds the recipient, a relayer and its fee as separate public inputs of its own circuit.

Hidden coins and amounts#

Zerocoin: anonymous coins from commitments and a proof of membership (Miers et al., 2013).

A user mints a zerocoin by paying a fixed amount to the ledger together with a commitment \(C = g^S h^r\) to a random serial number \(S\). To spend it, the user reveals \(S\) and proves in zero knowledge that it knows the opening of some minted coin with that serial, without saying which. The ledger records spent serials, so a coin cannot be spent twice, but the spend cannot be linked to its mint: every coin ever minted is in the anonymity set.

Miers, Garman, Green and Rubin made the proof constant-size by gathering the coins, hashed to primes, in an RSA accumulator \(A = u^{\\prod_i c_i} \bmod N\): each coin has a witness \(w = u^{\\prod_{j \ne i} c_j}\) with \(w^{c_i} = A\), and the spend proves knowledge of a witness for a committed coin.

Here the membership proof is instead a ring signature over every minted coin, linear in their number: \(C_i g^{-S} = h^{r}\) holds exactly for the coin being spent, so knowing \(r\) for one ring member is knowing the opening of one coin. The accumulator is shown with its witnesses, but the spend does not use it.

Confidential transactions: hidden amounts that still add up (Maxwell, 2015).

Each output’s amount is replaced by a Pedersen commitment \(C = g^{v} h^{r}\). Commitments multiply as their amounts add, so anyone can check that a transaction creates no money,

\[\begin{split}\\prod_{\text{in}} C_i = g^{\text{fee}} \\prod_{\text{out}} C_j ,\end{split}\]

as long as the sender chooses the blinding factors to cancel. That check alone is not enough: amounts are numbers modulo the group order \(q\), so an output of \(q - 1\), that is \(-1\), lets another output hold one coin more than was paid in. Every output therefore carries a range proof that its amount is small. Maxwell’s proof commits to each digit and proves, with a ring signature over \(\\{C_k, C_k / g^{2^k}\\}\), that one of them is a pure \(h^{r_k}\), so the digit is 0 or 1; the digit commitments multiply back to \(C\).

Elements and Liquid use base-4 digits joined into one Borromean ring signature; here every bit has its own two-member ring signature. Bulletproofs (see blockchainkit.proofs) later made the proof logarithmic.

Ring Confidential Transactions: hiding the input and the amounts at once (Noether, 2016).

Monero hid which output a transaction spends with linkable ring signatures, but amounts stayed public, and a ring could only mix outputs of the same denomination. RingCT puts every amount in a Pedersen commitment, as confidential transactions do, and must then prove the amounts balance without saying which ring member is the input.

It does so with a second column in an MLSAG signature. Each ring member \(i\) is a pair (one-time key \(P_i\), amount commitment \(C_i\)), and the second column’s key is

\[\begin{split}Z_i = \frac{C_i}{g^{\text{fee}} \\prod_j C^{\text{out}}_j} ,\end{split}\]

which, for the real input whose amount equals the outputs plus the fee, is \(h^{z}\) with \(z\) the difference of blinding factors. Signing both columns with one ring of challenges proves the signer knows the key of some \(P_i\) and the \(z\) of the same \(Z_i\), so that member’s amount balances. The key image of \(P_i\) stops double spends.

This model has one input per transaction; Monero gives each input a pseudo-output commitment so several inputs balance together, and since 2019 it uses CLSAG and Bulletproofs in place of MLSAG and digit-wise range proofs.

Mimblewimble: no addresses, no amounts, and a chain that forgets spent outputs (2016).

An anonymous author, “Tom Elvis Jedusor”, noticed that in a confidential transaction the blinding factors can serve as the keys. An output is just a commitment \(C = g^{v} h^{r}\), owned by whoever knows \(r\). If a transaction balances, the outputs divided by the inputs (and \(g^{\text{fee}}\)) leave \(h^{k}\) with \(k\) the change in blinding. The parties prove they know \(k\) by a Schnorr signature with the excess \(E = h^{k}\) as public key, recorded in a kernel. Nothing else is needed: no addresses, no scripts, no amounts.

Because only the sums matter, transactions merge non-interactively into one, and an output created and spent in the merged set cancels with its input. This cut-through lets a node discard every spent output yet still check that

\[\begin{split}\frac{\\prod \text{outputs}}{\\prod \text{inputs}} \\, g^{\text{fees} - \text{minted}} = \\Big(\\prod_k E_k\\Big) h^{\text{offset}} .\end{split}\]

Each transaction moves a random offset out of its kernel, as Grin does, so that merged transactions cannot be split back apart by matching kernels to subsets of inputs and outputs. Real Mimblewimble chains also attach a range proof to every output; see confidential.
