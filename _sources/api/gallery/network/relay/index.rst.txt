Block and transaction relay
---------------------------

Announcing instead of flooding, why propagation delay causes forks, compact
blocks, and hiding where a transaction came from.

    <div class="sphx-glr-thumbcontainer" tooltip="The simplest relay floods: every peer forwards a new block over each of its links, so a peer with eight neighbors may receive it eight times. The first Bitcoin client instead announces: it sends a small inv message carrying the block&#x27;s hash, and sends the block only to peers that ask for it with getdata. Each peer downloads each block once.">

Since blocks are found as a Poisson process, the chance of a fork per block is about 1 - exp(-delay / interval).">

    <div class="sphx-glr-thumbcontainer" tooltip="By the time a block is found, peers have usually already received most of its transactions as they were broadcast. Matt Corallo&#x27;s compact blocks (BIP 152) send only the header and a 6-byte short ID per transaction; the receiver rebuilds the block from its mempool and asks for the few it lacks. Short IDs are salted per block, so an attacker cannot craft transactions whose IDs collide in every block.">

Bojja Venkatakrishnan, Fanti and Viswanath proposed Dandelion: first pass the transaction along a random path (the stem), each hop continuing with a fixed probability, and only then diffuse it (the fluff). Spies then see the end of the stem.">
